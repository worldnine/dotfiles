# 機能実装の並列委任（herdr-delegate）

新規機能を herdr worktree + 複数エージェント（pi）に並列実装させ、オーケストレータが統合するワークフロー。2026-08 に ashiato リポジトリ（Rust TUI）で read ビュー機能を実装したセッションから蒸留した。

**前提:** herdr 実行環境（`test "${HERDR_ENV:-}" = 1`）。herdr の CLI 仕様は herdr スキルが権威なので、まず [herdr スキル](../herdr/SKILL.md) を読むこと。各フェーズで `herdr --help` / `herdr <group>` で現行 CLI を確認する。

---

## Phase 0: 分解と契約（最重要・ここが成否を分ける）

### 0.1 モジュール境界で分解する

- **孤立モジュール**（新規ファイルに閉じる。例: ログパーサー）と**統合側**（既存ファイルに広く触れる。例: TUI のビュー追加）に分ける
- 孤立モジュールは衝突リスクゼロで先にマージできる
- 統合側が複数になる場合は同一ファイルを触らせない（main.rs 系は 1 エージェントまで）

### 0.2 API 契約を先に固定する（オーケストレータの仕事）

並列開発が機能する条件は**公開 API をオーケストレータが最初に書き下す**こと。

- 公開シグネチャ（型・関数・意味論）をプロンプトにそのまま記載する
- 実装側エージェント: 「シグネチャと意味論は厳密に一致させること」と明示
- 統合側エージェント: **スタブ実装を書いて進める**と明示（「マージ時に本実装に差し替わる。スタブは契約の意味論を満たす簡易実装で良い。UI テストの期待値は契約に合わせる。スタブの癖に合わせない」）

### 0.3 fixture が契約の正典

- 共通テストデータ（両エージェントが使う fixture）を**オーケストレータが main に事前コミット**する
- fixture の**期待パース結果**（「この fixture からはこう出る」）を文書化して両プロンプトに記載
- 両エージェントが同じデータ・同じ期待値で実装とテストを書く → マージ後に実装を差し替えても統合側のテストが green（契約が機能した証明になる）
- fixture は実機のログ/出力形式を模したものにし、エージェントには「実機のディレクトリ/ログを確認して実装し、形式が fixture と食い違ったらレポートに書け」と指示する（形式の実測はエージェントにさせる）

### 0.4 ベースライン

- テスト件数・clippy 警告数を控える（「新規警告ゼロ」「既存テスト green のまま」の比較元）

## Phase 2: herdr セットアップ + タスク投入

### 2.1 同期ゲート → worktree 作成（1 つずつ）

**同期ゲート（worktree 作成前に必ず実行）**

実戦事例（36 PR を 4 wave で並列実装したスプリント）で全 PR が全ファイル衝突して破棄された唯一の大失敗は stale main が原因。前 wave のマージ後に fetch していないと、古い HEAD から worktree が分岐する。エージェント側では検出不能（テストも通る。内部整合性は正しくてもベースが古い）。

```bash
git -C <repo> fetch origin main
git -C <repo> rev-parse main           # ローカル HEAD
git -C <repo> rev-parse origin/main    # リモート HEAD
```

- 一致 → そのまま進む
- ローカルが遅れている → `git -C <repo> merge --ff-only origin/main`
- ff できない（ローカルが分岐済み）→ 停止して人間の判断を仰ぐ

エージェントの検証コマンドは内部整合性しか保証しない。ベースラインの正しさは開始前にオーケストレータが保証する。

```bash
herdr worktree create --cwd <repo> --branch feat/<slug> --base main \
  --path <worktree-path> --label <label> --no-focus
```

レスポンス JSON から `pane_id` / `workspace_id` / `checkout_path` を読む（ID を推測しない）。

### 2.2 エージェント起動

```bash
herdr pane rename <pane_id> "<label>"
herdr pane run <pane_id> "pi"          # 実行ファイル名だけ。argv でタスクを渡さない
herdr agent wait <pane_id> --until idle --timeout 90000
```

### 2.3 タスクプロンプト（自己完結・ファイル経由で投入）

**エージェントはこの会話の文脈を持たない。** プロンプトだけで全て伝わるようにする:

```
<リポジトリ名>（<言語/種別>）の worktree で作業するエージェントです。

# タスク

## fixture と期待結果（正典。src/testdata/ にコミット済み）

## 制約
- 変更は <ファイル列挙> のみ。無関係なリファクタリング・スタイル変更はしない
- 既存 <N> テストが全て green のまま（<テストコマンド>）
- <clippy 相当> で新規警告ゼロ（ベースラインは <N> 件）
- 依存追加は不可（足りないものがあれば報告のみ）
- コメントは日本語。既存文体（「なぜそうするか」）を尊重
- 完了したら日本語のコミットメッセージでコミット。push・マージはしない
- 完了レポートは `HANDOFF.md` として worktree ルートに書き、コミットに含める（オーケストレータはこれを正典として読む。pane の出力は参照しない）
  - 内容: 実装内容 / 実機確認の結果 / テスト結果（件数）/ clippy 警告数 / fixture と実機の食い違い（あれば）
  - 統合側に必要な情報（呼び出し規約・動作確認手順・残タスク）も書く
```

## Phase 3: 監視

### 3.1 状態ポーリング

```bash
for p in <pane1> <pane2>; do \
  herdr agent get $p | python3 -c "import json,sys; print(json.load(sys.stdin)['result']['agent'].get('agent_status'))"; done
```

- `done` / `idle` = 完了（どちらも完了として扱う）
- 進捗確認は `herdr agent read <pane> --source recent-unwrapped --lines 40`
- コミット済みかは worktree で `git log --oneline -2` / `git status --short`（作業ツリーに未コミットが残っていればまだ作業中）

### 3.2 ハングからの回復（実践で踏んだ罠）

- **pty スモークテストの無限ハング**: エージェントが `printf 'q' | script -q /dev/null <tui-binary>` のようなテストをすると、キーが TUI に届かず無限に待つ。steering を送っても**実行中の bash ツールが返るまで処理されない**
- 回復手順: `herdr pane send-keys <pane> "ctrl+c"` が効かないこともある → `ps aux | grep <バイナリ名>` でプロセスツリーを特定し `kill`（エージェントの bash ツールがエラーで返り、steering が処理される）
- pty での対話テストは最初から「不要」と指示しておくのが最善

### 3.3 steering

```bash
herdr agent prompt <pane_id> '<追加指示>'
```

（`--wait` は失敗することがある。付けなくても届く）

## Phase 4: マージ前レビュー（エージェントの成果も敵対的に）

```bash
git -C <worktree> log --oneline -3
git -C <worktree> diff main...HEAD --stat   # 範囲外ファイルがないか
git -C <worktree> status --short            # 未コミット残骸がないか
git -C <worktree> show HEAD:HANDOFF.md      # 成果物を正典として読む（pane のテキストは参照しない）
```

確認点:

- **スコープ違反の典型: `cargo fmt` が無関係ファイルを整形する**。git.rs 等の無関係ファイルが「整形だけ」の差分になっていたら revert 指示 or マージ時に除外
- 新規 `unwrap()` / `expect()` が本番コードにないか（テスト内は許容）
- テストが「本番構造を再現」しているか（fixture の期待結果をそのままアサートしているか）
- フレーク源（実時間依存・固定パス）を導入していないか

## Phase 5: 順次マージ

### 5.1 順序

**孤立モジュール → 統合側**。各マージ前に全テスト PASS を確認。

**依存があるタスクは wave に分解する**（契約を共有するスライスは並列にしない。worktree はファイル衝突しか防げない。論理衝突は防げない）:

- Wave 1 = 互いに独立なタスク群を並列 → 全部マージ
- Wave 境界でユーザーにレビューを挟む（人間のレビューが律速。エージェントは 15 分、レビューは数時間）
- Wave 2 以降は**更新済み main から**分岐（Phase 2.1 の同期ゲートを必ず再実行）

```bash
git merge --no-ff <branch> -m "Merge branch '<branch>': <日本語の要約>"
```

（マージ規約はリポジトリ既存の流儀に合わせる）

### 5.2 スタブ vs 本実装の衝突解決

統合側のスタブファイルと本実装が **add/add 衝突**する:

```bash
git checkout main -- <file>   # 本実装を採用（スタブは捨てる）
git add <file>
```

呼び出し側（統合側）のテストが本実装に対して green なら契約が機能した証拠。`main.rs` 等の `mod readlog;` 1 行は両者同一なので自動解決されることが多い。

### 5.3 マージ後

- 全テスト + clippy が**ベースラインから増えていない**こと
- オーケストレータ担当分（docs・プラグイン・キーバインド等）は直接 main で対応

## このワークフローから学んだ要点

- **同期ゲートが全 PR を守る**: stale main からの分岐はエージェントには検出不能（テストも通る）。worktree 作成前に fetch + ff-only を必ず実行する
- **成果物（HANDOFF.md）を正典にする**: pane のテキストは消えうる。判断はコミットされたファイルと照合する
- **契約ファーストの並列開発は機能する**: fixture = 契約の正典、期待結果を文書化、統合側はスタブで進める。マージで実装を差し替えても全テスト green になった
- プロンプトの「変更範囲」制約は、`cargo fmt` のような機械的なスコープ違反を防げない → マージ前レビューで回収する（フォローアップで revert 指示を出せばエージェントも直す）
- エージェントの実機検証（pty テスト）はハングしがち。最初から「不要」と明示するか、タイムアウトを付ける
- ログ形式・slug 規則のような**実機でしか分からない仕様はエージェントに実測させてレポートに含めさせる**（推測で書かせない）
- エージェントが「正典 fixture の期待結果」を満たすテストを書いていれば、実装の差し替え・統合が安全になる。fixture 設計（正典化）への投資が並列開発の信頼性を決める
- 機能の価値判断はエージェントではなくユーザーとオーケストレータで行う。不要と判断した機能は**タグを打ってから撤去**し、履歴に残す（git は「なかったこと」にしないための道具）
