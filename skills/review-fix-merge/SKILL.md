# レビュー → 並列修正 → マージ（review-fix-merge）

コードレビュー指摘を herdr worktree + 複数エージェントで並列修正し、main に統合する一連のワークフロー。2026-08 に ashiato リポジトリ（Rust TUI）で実践したセッションから蒸留した。エージェントは pi を使用（利用可能ならどのエージェントでもよい。ユーザー指定があればそれに従う）。

**前提:** herdr 実行環境（`test "${HERDR_ENV:-}" = 1`）。herdr の CLI 仕様は herdr スキルが権威なので、まず [herdr スキル](../herdr/SKILL.md) を読むこと。各フェーズで `herdr --help` / `herdr <group>` で現行 CLI を確認する。

---

## Phase 0: 敵対的レビュー

### 0.1 事前調査

1. ファイル一覧と行数（`find src -name "*.rs" | xargs wc -l | sort -n` 等）
2. `git log --oneline -15` — 最近の変更と**マージコミットの命名規約**（例: `Merge branch 'worktree/...': 日本語要約`）を把握。マージ時に同じ流儀を使う
3. README / 仕様書の主張とコードの対応（仕様は「こうあるべき」の正典。コードが仕様に追いついていない箇所を探す）
4. **ベースライン取得**: テスト実行（`cargo test --locked` 等）と clippy の警告一覧を控える。後の「新規警告ゼロ」検証の比較元になる
5. **フレーク検査（並列実行の前提確認）**: テストが複数 worktree の同時 `cargo test` に耐えるか、コードで洗い出す（`grep -rn "Instant::now()\|temp_dir().join(\"" src/` 等）。実時間依存・固定パスがあれば **エージェント投入前に直す**（投入後に直すと全エージェントが同じフレークを踏んで報告し、マージ前検証も全 FAIL になる）

### 0.2 探索カテゴリ

| カテゴリ | 狙いどころ |
|---|---|
| 不変条件の破れ | 「この値は常に File 行」等のコメント上の不変条件が、ループ境界で破れる箇所（move_up が Separator に着地） |
| ドキュメント/実装のドリフト | help テキスト・コードコメント・実装・テストの 4 者が食い違う箇所（`{{}}` 問題）。テストが「実装の意図」と「文書化された仕様」のどちらを固定しているかも確認 |
| 堅牢性 | raw mode 中の死キー（Ctrl+C）、シグナル/パニック時のターミナル復旧欠如、`expect` の失敗モードが実は存在し得る（DST で存在しないローカル時刻）、型先行入力のドロップ |
| セキュリティ | シェルクォート、プレースホルダ置換の再走査（単一パスか）、`sh -c` への引数渡し |
| パフォーマンス | キーストローク毎の O(n) 再計算、ループ内での再割り当て、UI スレッドのブロック |
| リソース | EPIPE 処理、子プロセスの fd 継承、バックオフが回復しない、変更検出シグネチャの穴（mtime+size 同一の編集を見逃す） |
| テストの盲点 | **テストデータが本番構造を再現していない**箇所（区切り線ゼロの visible で移動をテスト→区切り線バグが未検出）。UI の特徴的な構造物ほどテストから欠落しがち |
| テストの隔離（並列フレーク） | 実時間依存（`Instant::now()` との比較、sleep）、固定パス（`temp_dir().join("固定名")` — worktree が別でも同一マシンの TMPDIR は共有され truncate 競合）、環境変数・ポート依存のテストは、複数 worktree の同時 `cargo test` で確実にフレークする |

### 0.3 検証ルール（最重要）

**報告するバグは必ず実行または文字単位のトレースで確認する。** 読んだだけの推測は誤る（`{{}}` の挙動は最初のトレースで誤り、実機実行ではじめて正しい挙動が判明した）。方法:

- 最小再現コード（rustc のスクラッチファイル、一時テスト）で挙動を実証
- 既存のテストヘルパを流用した一時テスト（後で削除）
- どうしても実行できない場合は文字単位でトレースし、「実行していない」ことを報告に明記

### 0.4 報告フォーマット

重要度（🔴 毎回踏む/仕様違反、🟠 堅牢性・限定条件、🟡 低頻度・軽微、🟢 スタイル）→ ファイル:行 → 再現手順 → 修正案 → テスト盲点。最後に「良かった点」も公平に書く。指摘番号を振り、後の worktree 割り当てで参照する。

## Phase 1: worktree 割り当て計画

### グルーピング規則

- **同一ファイル・同一領域を触る指摘は 1 つの worktree にまとめる**（別々にするとマージで衝突する）
- **孤立モジュール（1 ファイルに閉じる変更）は独立 worktree** — 衝突リスクゼロで最初にマージできる
- **テストモジュールは全員が末尾に追記するため衝突の温床**。複数 worktree が main.rs を触るならマージ時の手動解決を前提とし、解決担当（自分）がいることを計画に含める
- 設計判断が必要な指摘はエージェントに選択肢 (a)/(b) と判断基準を与える（自由裁量でやらせない）
- 小さなドキュメント変更などはエージェントに回さず、**オーケストレータがマージ後に直接 main で対応**

### 計画の提示

エージェント起動前に、テーブル（ブランチ × 内容 × 衝突リスク）で計画をユーザーに見せる。エージェント種別の指定があれば従う。

## Phase 2: herdr セットアップ + タスク投入

### 2.1 worktree 作成

```bash
herdr worktree create --cwd <repo> --branch fix/<slug> --base main \
  --path <worktree-path> --label <label> --no-focus
```

- レスポンス JSON から `pane_id` / `workspace_id` / `checkout_path` を読む（ID を推測しない）
- 1 つずつ作成して pane_id を記録（ループ内で JSON から抽出）
- `--no-focus` でユーザーのフォーカスを奪わない

### 2.2 エージェント起動

```bash
herdr pane rename <pane_id> "<label>"
herdr pane run <pane_id> "pi"          # 通常の実行ファイル名だけ。argv でタスクを渡さない
herdr wait agent-status <pane_id> --status idle --timeout 30000
```

起動後、`herdr pane get <pane_id>` で `agent` が検出され `agent_status` が `idle` であることを確認してから投入する。

### 2.3 タスクプロンプト（自己完結テンプレート）

**エージェントはこの会話の文脈を持たない。** プロンプトだけで全て伝わるようにする:

```
<リポジトリ名>（<言語/種別>）のレビュー指摘 N 件を修正してください。作業ディレクトリはこの worktree（ブランチ <branch>、main から分岐済み）。まず <テストコマンド> が通ることを確認。

【バグ】<ファイル:行> <現象> <再現手順> <期待動作と実際の動作>

【修正方針】<方針。選択肢があるなら (a)/(b) と判断基準>

【テスト】<追加すべき回帰テストの指針。既存テストの構造（どのモジュールの末尾か）を明示>

【既知フレーク】（ある場合のみ）<テスト名> は実時間依存で、並列実行時に落ちることがある（本件と無関係。個別実行でパスすれば OK。フレークと自分の変更の区別を報告に含めること）

【制約】
- 修正範囲はこれとテストに限定。無関係なリファクタリング・スタイル変更をしない
- 既存コメントの文体（「なぜそうするか」の説明）を尊重
- 最後に <テストコマンド> 全パス、<clippy 相当> で新規警告ゼロを確認
- 完了したら日本語のコミットメッセージでコミットして報告
- main へのマージ・push はしないこと（オーケストレータが行う）
```

並列で投入する場合も、**1 pane ずつ完了確認してから次を投入**しなくてよい（投入自体は順不同で可。ただし各 pane の `wait --status idle` は必ず挟む）。

## Phase 3: 監視

### 3.1 状態ポーリング

```bash
for i in $(seq 1 20); do sleep 30; \
  for pane in <pane1> <pane2> ...; do \
    s=$(herdr pane get $pane | python3 -c "import json,sys; print(json.load(sys.stdin)['result']['pane'].get('agent_status'))"); \
    echo "$pane: $s"; done; done
```

- バックグラウンドタブの完了は `done`、見られていると `idle`。どちらも完了として扱う
- **長すぎる working（他より明らかに遅い）は `herdr pane read <pane> --source recent-unwrapped --lines 40` で進捗を確認**。設計判断に迷っているか、実機検証をしている（良い兆候）かの判断に使う

### 3.2 マージ前 diff レビュー

**エージェントの成果も敵対的にレビューする。** マージ前に必ず:

```bash
git -C <worktree> log --oneline -3        # コミットが 1 個でスコープ通りか
git -C <worktree> diff main...HEAD        # 範囲外変更・新規パニック・テストの質を確認
git -C <worktree> status --short          # 未コミットの残骸がないか
```

確認点: 指摘の意図通りか / スコープクリープがないか / テストが本番構造を再現しているか / 新しい `expect` や `unwrap` を導入していないか / 既存テストを弱体化していないか。

## Phase 4: マージ

### 4.1 事前テスト

マージ前に各 worktree でテストを**並列バックグラウンドで**実行:

```bash
(cd <worktree> && cargo test --locked -q > /tmp/test-<name>.log 2>&1 && echo PASS || echo FAIL) &
```

**並列実行で FAIL が出たら、失敗テストを確認してから直列で再実行する**（並列負荷起因のフレークは直列では通る）。失敗が既知フレーク（実時間依存等）なら、**マージ前に修正してからマージする**（修正しないままマージすると CI が不安定になる。修正はオーケストレータが main で直接行い、既存テストの修正なら worktree マージ後に回してもよいが、CI 安定化を優先する）。フレーク修正の正攻法はタイムスタンプ偽装ではなく**閾値・クロックの注入**（下記「学んだ要点」参照）。

### 4.2 マージ順序とコミット

- **孤立ファイル → 小さい変更 → 大きい変更** の順。全テスト PASS を確認してから次
- `git merge --no-ff <branch> -m "Merge branch '<branch>': <日本語の要約>"` — リポジトリ既存のマージ規約に合わせる

### 4.3 コンフリクト解決の教訓（実践で踏んだ罠）

1. **sed の行番号削除は行ズレを起こす**。複数マーカーを 1 回の `sed -i '' 'Nd;Md'` で消すと、前の削除で番号がずれ、**閉じ括弧などのコードを誤って消す**。削除後は必ずマーカー数（`grep -c "^<<<<<<<\|^=======\|^>>>>>>>"`）と境界付近を確認。edit ツール（正確なテキスト一致）を優先する
2. **両ブランチが同一関数を変更していたら、両方の意図を手動統合する**（例: TermGuard 化 × enter_tui_modes 抽出 × scanning 描画の 3 つの意図を 1 つの run() に合成）。片方の解決を選ぶと片方の修正が黙って消える
3. **テストが通る前にコミットしない**。もし通らない状態でコミットしてしまったら、修正後に `git commit --amend --no-edit` で即座に直す
4. 解決後: マーカー 0 確認 → `cargo test` → コミット。マージ由来の新規 clippy 警告（例: `derefed type is same as origin`）もこの時点で潰す

### 4.4 全マージ後

- `cargo test` 全パス + **clippy 警告がベースラインから増えていない**ことを確認
- オーケストレータ担当分（ドキュメント等）を直接 main にコミット
- 作業ツリーがクリーンであること、push していないこと（push は明示指示があるまでしない）

## Phase 5: 報告

- テーブル: ブランチ × 指摘番号 × 対応内容 × 追加テスト数
- テスト数・clippy の差分（ベースライン比）
- コンフリクトの発生箇所と解決方針
- 残件リスト（未対応の軽微指摘、仕様判断が必要な項目）

**クリーンアップの作法:** 作成した worktree / workspace / pane は勝手に削除しない。ユーザーに存在を伝え、削除コマンド（`herdr worktree remove --workspace <ID> --force` 等）を提示して任せる。

## このワークフローから学んだ要点

- レビューで見つけたバグは「再現してから」報告する。トレースの取り違えは実機実行でしか暴けない
- テストデータが本番構造を再現していないと、その構造特有のバグは全員が見逃す（区切り線バグはレビューでもエージェント修正でも気づかれず、私のレビューでのみ発見された）
- エージェントへの指示は選択肢と判断基準まで書く。自由裁量にするとスコープが膨らむ
- マージの衝突は「誰がどの領域を触るか」の計画で減らせるが、テストモジュールのような共有領域は必ず衝突する。解決担当が自分であることを前提に進める
- シグナルハンドラのような低レベル領域の修正はエージェントが実機検証（pty テスト）まで行うことがある。時間がかかっても良い成果になりがちなので、進捗を read で確認しながら待つ
- **実時間依存のテスト（`t.elapsed() < 400ms` 等）は並列負荷で確実にフレークする**。エージェント 5 台並列の実践では全員が同じフレークを踏み、マージ前検証も全 FAIL になった（直列再実行では全 PASS）。フレークの「事前検出 → エージェント投入前に修正」が最善。修正の正攻法は閾値・クロックをフィールド/引数に注入してテストから広げられるようにすること。**タイムスタンプの backdate 偽装は、偽装と実行の間のスレッド停止を防げず不十分**（実測で判明）
- **固定 $TMPDIR パスを使うテストは worktree が別でも競合する**（同一マシンの TMPDIR は共有され、`File::create` の truncate が他プロセスの読みを壊す）。tempfile 一択
